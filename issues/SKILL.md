# Issues

Break a plan into independently-grabbable issues using vertical slices (tracer bullets).

The tracker and its label vocabulary come from `AGENTS.md` and `docs/agents/issue-tracker.md`. If they are not configured, run the `triage` skill's setup mode first. Every issue posted must open with:

```
> *This was generated by AI.*
```

## 1. Gather context

Work from whatever is already in the conversation. If the user passes an issue reference (number, URL, or path), fetch it and read the full body and comments.

## 2. Explore the codebase

If you have not already, explore to understand the current state. Issue titles and descriptions should use the project's domain glossary vocabulary and respect ADRs in the area.

## 3. Draft vertical slices

The default failure here is **horizontal slicing** — "add the schema", "add the API", "add the UI". Those produce issues that cannot be finished, demoed, or verified alone. Cut the other way.

<vertical-slice-rules>
- Each slice delivers a narrow but COMPLETE path through every layer (schema, API, UI, tests)
- A completed slice is demoable or verifiable on its own
- Prefer many thin slices over few thick ones
</vertical-slice-rules>

Slices are `HITL` or `AFK`. HITL requires human interaction — an architectural decision, a design review. AFK can be implemented and merged without it. Prefer AFK where possible.

## 4. Check the breakdown with the user

Present the proposed breakdown as a numbered list. For each slice:

- **Title** — short descriptive name
- **Type** — HITL / AFK
- **Blocked by** — which other slices must complete first
- **User stories covered** — if the source material has them

Then ask:

- Does the granularity feel right? (too coarse / too fine)
- Are the dependency relationships correct?
- Should any slices be merged or split further?
- Are the right slices marked HITL vs AFK?

Iterate until the breakdown is approved.

## 5. Publish

For each approved slice, publish a new issue. Apply the `needs-triage` role so it enters the normal triage flow.

Publish in dependency order (blockers first) so you can reference real issue identifiers in "Blocked by".

An issue body is read by someone deciding whether to pick it up. No restating the title, no narrating how the slice was chosen, no defending the breakdown. A section with nothing behind it is deleted.

## Parent

## What to build

A concise description of this vertical slice. Describe the end-to-end behavior, not layer-by-layer implementation.

## Acceptance criteria

- [ ] Criterion 1
- [ ] Criterion 2
- [ ] Criterion 3

## Blocked by

Or "None - can start immediately" if no blockers.

</issue-template>

Do NOT close or modify any parent issue.
